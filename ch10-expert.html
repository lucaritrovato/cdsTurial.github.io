I capisaldi del livello senior: il modello draft che governa le UI editabili, gli eventi che disaccoppiano i service, la multitenancy che permette di servire N clienti con una sola app, l'extensibility che fa scegliere al cliente cosa estendere. Il modello Draft di CAP

Nelle applicazioni enterprise capita continuamente questo scenario: un utente apre un form, compila tre campi su quindici, viene chiamato in riunione, chiude il browser. Domani vuole riprendere da dove aveva lasciato. Senza draft, quei dati sono persi — o peggio, sono già salvati a metà nel database "buono" e qualcun altro ci sta lavorando sopra senza saperlo.

Il Draft Handling di CAP risolve questo problema in modo dichiarativo: una singola annotazione attiva un meccanismo completo di salvataggio intermedio, locking ottimistico, recovery e attivazione finale. È uno dei feature più potenti dell'intero stack — e uno dei più sottovalutati.

Il modello concettuale: ogni entity con draft attivo vive in due stati simultanei:

  • Active — il record "ufficiale" visibile a tutti, persistito nella tabella principale.
  • Draft — una copia in lavorazione, persistita in una tabella shadow EntityName_drafts, visibile solo all'utente che la sta editando.

L'utente lavora sul draft, lo salva ogni 2 secondi (autosave automatico di Fiori Elements), e quando è pronto fa activate: a quel punto il draft viene "trasferito" sulla active version e cancellato. Se decide di scartare, basta una discard.

Perché è importante saperlo bene

Se sviluppi con Fiori Elements, il 90% delle entity editabili avranno @odata.draft.enabled. Capire cosa succede sotto è la differenza tra un sviluppatore CAP medio e uno senior. La gran parte dei bug enterprise — locking strani, dati che spariscono, handler che si triggerano due volte — vengono da una comprensione superficiale del draft model.

@odata.draft.enabled in dettaglio

L'attivazione è banale:

.cds 
service AdminBookService @(requires: 'admin') {{
  
  @odata.draft.enabled
  entity Books as projection on db.Books;
  
  @odata.draft.enabled
  entity Authors as projection on db.Authors;
}}

Da questa singola riga CAP deriva automaticamente:

  • Una tabella shadow AdminBookService_Books_drafts con la stessa struttura più colonne tecniche.
  • Le bound action standard: draftEdit, draftActivate, draftPrepare, e l'unbound discardDraft.
  • Una view di unione che presenta Books filtrando per utente: ognuno vede i suoi draft + tutti gli active.
  • Locking ottimistico via HasDraftEntity, IsActiveEntity, HasActiveEntity — campi virtuali che il client interroga.

Le colonne tecniche aggiunte sulla shadow table:

.sql 
CREATE TABLE ADMINBOOKSERVICE_BOOKS_DRAFTS (
  ID            NVARCHAR(36) NOT NULL,
  title         NVARCHAR(100),
  price         DECIMAL(9,2),
  -- ... tutti i campi della entity originale ...
  
  -- Campi tecnici draft
  DraftAdministrativeData_DraftUUID  NVARCHAR(36),
  HasActiveEntity                    BOOLEAN,
  IsActiveEntity                     BOOLEAN,
  
  PRIMARY KEY (ID, IsActiveEntity)
);

CREATE TABLE DRAFTADMINISTRATIVEDATA (
  DraftUUID          NVARCHAR(36) PRIMARY KEY,
  CreationDateTime   TIMESTAMP,
  CreatedByUser      NVARCHAR(256),
  LastChangeDateTime TIMESTAMP,
  LastChangedByUser  NVARCHAR(256),
  DraftIsCreatedByMe BOOLEAN,
  InProcessByUser    NVARCHAR(256)
);
PK composita

Nota la primary key (ID, IsActiveEntity): è il trucco che permette a draft e active di coesistere con lo stesso ID. Quando attivi il draft, CAP fa una DELETE + INSERT atomica per spostare il record dalla shadow alla active.

Lifecycle dei draft

Il ciclo di vita completo di un draft, visto dal punto di vista del client OData:

.http 
# 1. CREATE: nasce direttamente come draft
POST /admin/Books
Content-Type: application/json

{{ "title": "In lavorazione" }}

# Response: ritorna l'entity con IsActiveEntity=false
{{
  "ID": "abc-123",
  "title": "In lavorazione",
  "IsActiveEntity": false,
  "HasActiveEntity": false,
  "HasDraftEntity": false
}}

# 2. PATCH: ogni 2 secondi, autosave
PATCH /admin/Books(ID=abc-123,IsActiveEntity=false)
{{ "price": 29.90 }}

# 3. EDIT: voglio editare un record già active
POST /admin/Books(ID=xyz-789,IsActiveEntity=true)/AdminBookService.draftEdit
# Crea un draft a partire dall'active, mantiene l'ID

# 4. ACTIVATE: trasferisce draft → active
POST /admin/Books(ID=abc-123,IsActiveEntity=false)/AdminBookService.draftActivate

# 5. DISCARD: butta via il draft
POST /admin/Books(ID=abc-123,IsActiveEntity=false)/AdminBookService.draftDiscard

Tre punti critici da memorizzare:

  1. CREATE in draft mode: in una entity draft-enabled, una POST non crea direttamente l'active version — crea un draft. L'active esiste solo dopo activate. Questo cambia tutta la semantica dei tuoi before('CREATE') handler.
  2. Locking automatico: quando un utente prende un draft (via edit o create), CAP segna InProcessByUser. Per default il lock dura 15 minuti dall'ultima modifica, configurabile via cds.drafts.cancellationTimeout.
  3. Garbage collection: i draft "abbandonati" vengono cancellati dopo un periodo configurabile (default 30 giorni). Esiste un job periodico cds.drafts.deletionTimeout.
Disabilitare il locking

In rari casi (es. user collaboration su stesso draft) puoi disabilitare il check con l'annotation @Common.DraftRoot.PreparationAction custom. Ma 9 volte su 10 il locking è quello che vuoi: previene corruzione dati.

Custom handlers per draft

Qui sta la trappola: nei tuoi handler devi distinguere se stai operando su draft o su active. CAP introduce eventi specifici per i draft:

.js 
const cds = require('@sap/cds');

module.exports = cds.service.impl(async function() {{
  const {{ Books }} = this.entities;

  // ✓ Triggerato SOLO sul draft, ad ogni autosave
  this.before('PATCH', Books.drafts, async req => {{
    // Validation in-progress, su dati ancora incompleti
    if (req.data.price && req.data.price < 0) {{
      req.error(400, 'Price cannot be negative', 'price');
    }}
  }});

  // ✓ Triggerato quando l'utente clicca "Save" (activate)
  // Qui i dati DEVONO essere completi e validi
  this.before('CREATE', Books, async req => {{
    // Questo si triggera sulla activation, NON sulla creation iniziale
    if (!req.data.title) {{
      req.error(400, 'Title is mandatory');
    }}
    if (req.data.price <= 0) {{
      req.error(400, 'Price must be positive');
    }}
  }});

  // ✓ Quando l'utente clicca "Edit" su un record esistente
  this.before('NEW', Books.drafts, async req => {{
    // Pre-popolazione campi tecnici
    req.data.lastEditor = req.user.id;
  }});

  // ✓ Sull'attivazione: hook custom dopo che il draft diventa active
  this.after('draftActivate', Books, async (data, req) => {{
    await this.emit('BookPublished', {{ ID: data.ID }});
  }});
}});
Errore comune: validation nel posto sbagliato

Se metti la validazione obbligatoria di title in before('PATCH', Books.drafts), l'utente NON potrà mai salvare il draft finché non avrà compilato title — ma l'autosave gira ogni 2 secondi! Risultato: errori a raffica sullo schermo. Le validation strict vanno in before('CREATE') e before('UPDATE') sull'entity active (cioè all'activate). Solo i check di formato leggeri (es. range numerici) vanno sul draft.

Una tabella per non confondersi mai:

EventoQuandoCosa metterci
NEW su .draftsClick su "Create" o "Edit"Pre-popolazione default
PATCH su .draftsAutosave (ogni 2s)Validation soft, calcoli intermedi
CREATE su entityClick su "Save" (activate da nuovo)Validation strict, business rules
UPDATE su entityClick su "Save" (activate da edit)Validation strict su update
CANCELClick su "Cancel" / discardCleanup risorse esterne

Eventi e messaging

CAP ha un sistema di eventi di prima classe. Puoi dichiarare eventi nel modello, emetterli dal codice, sottoscriverli in altri service — e tutto questo funziona in-process oppure attraverso un broker (Event Mesh, Kafka, Redis) senza cambiare il codice.

.cds 
service CatalogService {{
  
  entity Books as projection on db.Books;
  
  // Eventi dichiarati
  event BookOrdered {{
    book     : Books:ID;
    quantity : Integer;
    customer : String;
    timestamp: Timestamp;
  }}
  
  event StockDepleted {{
    book     : Books:ID;
    title    : String;
  }}
}}
.js 
// srv/catalog-service.js — emit
this.on('submitOrder', async req => {{
  const {{ book, quantity }} = req.data;
  
  const book_row = await SELECT.one.from(Books, book);
  if (book_row.stock < quantity) req.reject(400, 'Out of stock');
  
  await UPDATE(Books, book).set({{ stock: {{ '-=': quantity }} }});
  
  // Emit dopo l'update
  await this.emit('BookOrdered', {{
    book, quantity,
    customer: req.user.id,
    timestamp: new Date()
  }});
  
  const updated = await SELECT.one.from(Books, book);
  if (updated.stock === 0) {{
    await this.emit('StockDepleted', {{ book, title: updated.title }});
  }}
}});

// Subscribe nello stesso o altro service
this.on('BookOrdered', async msg => {{
  console.log(`Book ordered:`, msg.data);
  // Es. log audit, invia email, aggiorna analytics...
}});

// Subscribe cross-service
const catalog = await cds.connect.to('CatalogService');
catalog.on('StockDepleted', async msg => {{
  // Trigger riassortimento automatico
  await triggerReorder(msg.data.book);
}});
In-process vs broker

Per default gli eventi sono in-process (sync, stesso ciclo di vita della request). Quando colleghi un broker (vedi sotto) diventano asincroni e cross-service. Il codice resta identico: cambia solo la configurazione.

SAP Event Mesh & Kafka

Per andare oltre il singolo processo, CAP supporta nativamente tre broker:

.json 
// package.json — configurazione per profilo
{{
  "cds": {{
    "requires": {{
      "messaging": {{
        "[development]": {{ "kind": "file-based-messaging" }},
        "[production]":  {{ "kind": "enterprise-messaging" }},
        "[kafka]":       {{ "kind": "kafka" }}
      }}
    }}
  }}
}}

I tre kind disponibili:

  • local-messaging — default, in-process, una sola istanza.
  • file-based-messaging — sviluppo, fa partire un file watcher così più istanze locali si vedono.
  • enterprise-messaging — SAP Event Mesh, binding via service key BTP.
  • enterprise-messaging-shared — Event Mesh con topic shared.
  • redis — broker Redis Streams.
  • kafka — Apache Kafka (via @sap/cds-mbx-kafka o equivalente).

Topic naming convention per Event Mesh (rispetta CloudEvents):

text 
<namespace>/<service>/<event>

Esempio:
acme.bookshop/CatalogService/BookOrdered
acme.bookshop/CatalogService/StockDepleted
CloudEvents compliant

I messaggi emessi da CAP rispettano lo standard CloudEvents: questo significa che possono essere consumati da qualsiasi altro sistema che parla CloudEvents (Kyma, Knative, Azure Event Grid, ecc.) senza adapter custom.

Multitenancy: il modello mentale

Multitenancy in CAP non è un "feature" da attivare casualmente: è una decisione architetturale che cambia tutto. Prima di scriverla una sola riga, devi capire i modelli:

  • Single-tenant — una sola applicazione, un solo set di utenti, un solo database. Default di cds init.
  • Multi-tenant shared database — un'unica istanza dell'app serve N clienti, tutti i dati in un unico DB con colonna tenant che discrimina. Semplice ma rischioso: una query mal scritta espone dati cross-tenant.
  • Multi-tenant separate schemas — il modello SAP CAP "ufficiale". Ogni tenant ha il suo schema HDI completo, completamente isolato. Una sola applicazione, ma N container HDI. Questo è quello che ottieni con cds add multitenancy.
  • Multi-instance — un'istanza app + un DB separato per tenant. Massima isolazione ma costoso. Si usa per casi enterprise pesanti.

SAP CAP implementa il modello separate schemas: un'unica applicazione (Node.js, K8s pod) gestisce tutti i tenant, ma ogni tenant ha il suo HDI container HANA dedicato. Il routing per tenant avviene via subdomain o JWT claim.

Onboarding costoso

L'onboarding di un nuovo tenant in modello separate schemas crea un nuovo HDI container e ci deploya tutto lo schema. È un'operazione asincrona che dura 30-90 secondi e costa risorse HANA. Non è qualcosa da fare per ogni utente: tipicamente "tenant" = "organizzazione cliente".

@sap/cds-mtxs in pratica

Il pacchetto @sap/cds-mtxs (Multi-Tenancy and Extensibility Services) è il modulo che orchestra tutto. Aggiunta:

.bash 
cds add multitenancy

# Equivalente a:
npm i @sap/cds-mtxs
cds add xsuaa,approuter --for production

Cosa cambia nel progetto:

.yaml 
# mta.yaml estratto
modules:
  - name: bookshop-srv
    type: nodejs
    requires:
      - name: bookshop-uaa        # auth + tenant routing
      - name: bookshop-registry   # SaaS registry
      - name: bookshop-service-manager  # HDI per tenant
      
  - name: bookshop-mtx
    type: nodejs
    path: gen/mtx/sidecar
    # Microservizio sidecar per provisioning tenant
    
resources:
  - name: bookshop-service-manager
    type: org.cloudfoundry.managed-service
    parameters:
      service: service-manager
      service-plan: container

Il modello runtime: ogni request HTTP arriva con un JWT che contiene il tenant ID. CAP usa quel tenant per scegliere quale HDI container interrogare, in modo trasparente. I tuoi handler vedono req.tenant ma nei SELECT, INSERT ecc. non devi mai mettere il filtro: lo fa la connection pool.

.js 
// Nei handler, accesso al tenant
this.before('CREATE', Books, async req => {{
  console.log(`Creating book for tenant: ${{req.tenant}}`);
  // La query userà automaticamente il pool del tenant corretto
  await SELECT.from(Books); // → HDI container del tenant T
}});

// Operazioni cross-tenant: solo con super-user
await cds.tx({{ tenant: 'tenant-A' }}, async tx => {{
  await tx.run(SELECT.from(Books));
}});
MTX sidecar

Il sidecar bookshop-mtx è un microservizio dedicato che espone gli endpoint /-/cds/saas-provisioning e /-/cds/extensibility. Serve a separare le operazioni "di sistema" (provisioning tenant, deploy estensioni) dalle operazioni di business: così l'app principale non si blocca su un onboarding lungo.

Extensibility: estendere modelli

Multitenancy apre la porta a una feature ancora più potente: extensibility. Ogni tenant può estendere il modello dati dell'applicazione (aggiungere campi, entity, view custom) senza toccare il codice sorgente dell'app.

Caso d'uso classico: vendi una SaaS B2B. Il cliente Tenant-A vuole aggiungere un campo customerSegment a Customers, il cliente Tenant-B vuole una nuova entity LoyaltyProgram. Senza extensibility, dovresti fare branching o aggiungere tutti i campi e disabilitarli — un incubo. Con extensibility, ognuno estende il suo schema in isolamento.

Sintassi delle estensioni tenant-side:

.cds 
// extension.cds nel tenant A
using CatalogService from 'bookshop';

extend CatalogService.Books with {{
  customerSegment : String(20);
  internalNotes   : String(500);
}}

extend CatalogService with {{
  entity LoyaltyProgram {{
    key ID    : UUID;
    name      : String;
    threshold : Integer;
  }}
}}

Deploy dell'estensione tramite API MTX:

.http 
PUT /-/cds/extensibility/Extensions
Content-Type: application/json
Authorization: Bearer <admin-token-tenant-A>

{{
  "extensions": [{{
    "name": "customerSegmentExt",
    "content": "extend CatalogService.Books with { customerSegment: String(20); }"
  }}]
}}

Dietro le quinte CAP compila l'estensione, applica un ALTER TABLE allo schema HDI del tenant, ricarica i metadati per quella tenant: tutti i campi nuovi diventano immediatamente disponibili via OData. Il tenant B continua a non vederli.

Cosa NON si può estendere

Per ragioni di sicurezza e stabilità, da un'estensione tenant-side NON puoi: scrivere custom handler in JavaScript, modificare service path, rimuovere campi del modello base, cambiare le primary key. Le estensioni sono additive, mai distruttive.

Per consentire estensioni mirate (e bloccare quelle problematiche), il provider può annotare il modello base:

.cds 
@extensible
entity Books {{
  key ID    : UUID;
  title     : String;
  
  @extensible: false  // vietato estendere questo campo
  price     : Decimal;
}}

// Limitazioni granulari
@extensible: { fields: 10, fieldNames: ['custom_*'] }
entity Orders {{ ... }}
// Max 10 campi aggiunti, nomi devono iniziare con custom_

Feature toggles

Il feature toggle è un meccanismo per attivare/disattivare porzioni del modello a runtime per certe tenant o certi utenti, senza redeploy. Caso classico: vuoi lanciare una nuova feature in beta su 3 tenant, poi rolloutare al 50%, poi al 100%.

.cds 
// Modello con feature toggle
service CatalogService {{
  entity Books as projection on db.Books;
  
  @requires.feature: 'ai-recommendations'
  function getAIRecommendations(userId: String) returns array of Books;
  
  @requires.feature: 'advanced-search'
  entity SearchableBooks as projection on Books;
}}
.json 
// package.json — toggle config
{{
  "cds": {{
    "features": {{
      "ai-recommendations": {{ "enabled": false }},
      "advanced-search": {{ "enabled": true }}
    }}
  }}
}}

Override per tenant via API:

.http 
PATCH /-/cds/saas-provisioning/tenant/tenant-A
{{ "features": ["ai-recommendations", "advanced-search"] }}
Quando usarli

Feature toggle ≠ extensibility. Feature toggle è per il provider: tu sviluppi una feature, la flagghi, la attivi gradualmente. Extensibility è per il tenant: il cliente personalizza il suo schema. Spesso si combinano: il provider attiva la feature "custom-fields" via toggle, dopo di che il tenant può davvero estendere lo schema.

Performance tuning: l'arsenale completo

A questo punto della tua carriera CDS devi smettere di scrivere codice "che funziona" e iniziare a scrivere codice "che scala". Ecco l'arsenale completo:

1. Pushdown è tutto

La regola d'oro: fai elaborare ad HANA, non a Node.js. Una query CQL ben scritta viene pushed-down al DB; una query "smontata" in Node con loop diventa N+1 query.

.js 
// ❌ ANTIPATTERN: N+1 (1 query Books + N query Authors)
const books = await SELECT.from(Books);
for (const b of books) {{
  b.author = await SELECT.one.from(Authors, b.author_ID);
}}

// ✓ CORRETTO: 1 sola query con expand
const books = await SELECT.from(Books).columns(b => {{
  b.'*', b.author(a => {{ a.name }})
}});

2. Indici via annotazione

.cds 
@cds.persistence.index: [['title'], ['author_ID', 'year']]
entity Books {{ ... }}

// Genera due CREATE INDEX nello schema HDI

3. Pagination obbligatoria

Per default Fiori Elements pagina a 100. Ma se chiami SELECT.from da codice, ottieni TUTTO. Su tabelle grandi è suicidio.

.js 
// Sempre con limit + offset su dataset potenzialmente grandi
const page = await SELECT.from(Books).limit(100, 200);
// Oppure cursor-based per dataset enormi
const chunk = await SELECT.from(Books)
  .where({{ ID: {{ '>': lastId }} }})
  .orderBy('ID').limit(100);

4. Calcoli pesanti → Calculation View HANA

Se hai analytics aggregate complesse (rollup, partition, finestre temporali), non scrivere SELECT giganti in CDS. Costruisci una Calculation View nativa HANA e la includi via @cds.persistence.exists. È 10-100× più veloce e fa pieno uso dell'engine columnar.

5. Connection pooling

HANA Cloud ha limiti di connessioni. Configura il pool in modo realistico:

.json 
// .cdsrc.json
{{
  "requires": {{
    "db": {{
      "kind": "hana",
      "pool": {{
        "max": 10,
        "min": 2,
        "acquireTimeoutMillis": 3000,
        "idleTimeoutMillis": 30000
      }}
    }}
  }}
}}

6. $apply per analytics

Se il client (Fiori UI5 Analytical Table, SAC, Excel) supporta $apply, CAP pusha l'intero pipeline analitico al DB. Non c'è bisogno di scrivere endpoint custom: $apply=groupby((country),aggregate(revenue with sum as totalRevenue)) diventa una vera GROUP BY HANA.

Observability: log, trace, metrics

Per gestire un'app CAP in produzione devi vederla.

Logging strutturato

.js 
const LOG = cds.log('catalog-service');

LOG.info('Book ordered', {{ book: bookId, qty }});
LOG.warn('Low stock', {{ book: bookId, stock }});
LOG.error('Order failed', err);

// Configurazione livelli per profilo
// .cdsrc.json
// "log": { "service": "info", "db": "warn" }

Tracing distribuito

CAP supporta OpenTelemetry out-of-the-box. Ogni request HTTP, ogni query DB, ogni emit di evento diventa uno span con traceId propagato. Tu lo attivi così:

.bash 
npm i @cap-js/telemetry

# .cdsrc.json
# "requires": { "telemetry": true }

# Variabili env per export OTLP
export OTEL_EXPORTER_OTLP_ENDPOINT=https://otel-collector:4318
export OTEL_SERVICE_NAME=bookshop-srv

Metriche e health-check

CAP espone automaticamente:

  • /health — liveness probe (200 = up)
  • /ready — readiness (DB raggiungibile, MTX sidecar attivo, ecc.)
  • Metriche Prometheus opzionali via @cap-js/telemetry
Logging in HANA Cloud

Su BTP/Cloud Foundry i log finiscono nell'Application Logging service o nel Cloud Logging Service (Loki-backed). Su Kyma vai su un OTEL collector centrale. La cosa importante è sempre lo stesso: structured logging, mai concatenazioni stringa. Il traceId è la chiave per debuggare un problema cross-service.

Test strategy

Un'app CAP enterprise senza test è un'app rotta che non sai dov'è rotta. Tre livelli di test:

1. Unit test sui handler

.js 
// test/unit/catalog.test.js — usando vitest o jest
const cds = require('@sap/cds');
const {{ expect }} = cds.test('serve', 'CatalogService').in(__dirname, '../..');

describe('CatalogService', () => {{
  
  it('rejects negative price', async () => {{
    const {{ POST }} = cds.test;
    await expect(
      POST('/catalog/Books', {{ title: 'X', price: -5 }})
    ).to.be.rejectedWith(/positive/);
  }});

  it('computes discount on read', async () => {{
    const {{ GET }} = cds.test;
    const {{ data }} = await GET("/catalog/Books?$select=ID,price,discount");
    expect(data.value[0].discount).to.equal(data.value[0].price * 0.1);
  }});
}});

2. Integration test end-to-end

Usa SQLite in-memory per CI veloci, e un container HANA HXE / HANA Cloud trial per test "veri":

.bash 
# CI: SQLite, in-process, < 5 secondi
npm test

# Pre-prod: contro HANA Cloud trial
cds bind --to hana:bookshop-db
npm run test:integration

3. Contract test sulle API OData

Genera lo schema $metadata e verifica che non si rompa tra release:

.bash 
cds compile srv --to edmx > tests/fixtures/expected-metadata.xml

# In CI:
cds compile srv --to edmx | diff - tests/fixtures/expected-metadata.xml
# Se diff fallisce, qualcuno ha cambiato il contratto API senza accorgersene
Testing in pipeline

Il pattern più solido: unit con SQLite (veloci, ogni commit) → integration con HANA su pull request → smoke test post-deploy su ambiente staging. Mai pushare in produzione senza che almeno i livelli 1+2 siano verdi.

Il progetto finale: Library Management

Hai attraversato 10 capitoli. Ora un solo progetto che tocchi tutto. Non leggerlo: costruiscilo. È il modo in cui i topic si sedimentano in muscle memory.

Specifica funzionale

Library Management: una piattaforma SaaS B2B per biblioteche pubbliche. Ogni biblioteca (tenant) gestisce: il proprio catalogo libri, gli autori, gli utenti iscritti, i prestiti, le multe, gli eventi.

Roadmap suggerita (4-6 settimane part-time)

  1. Settimana 1 — modello dati completo (db/). cds watch + sqlite, niente UI.
  2. Settimana 2 — service layer (srv/) + custom handlers. Tutti i test unit verdi.
  3. Settimana 3 — UI annotations + Fiori Elements app. Browser-test ogni flow.
  4. Settimana 4 — Draft, eventi, validazioni cross-entity, regole di business.
  5. Settimana 5 — Deploy HANA Cloud, MTA, multitenancy con 2 tenant demo.
  6. Settimana 6 — Extension demo, observability, README finale.
Il vero metro

Quando il tuo progetto finale può: (1) onboarding di un nuovo tenant in < 2 minuti via API, (2) sopravvivere a un fault del DB con retry trasparente, (3) tracciare un'intera request HTTP attraverso log e trace fino alla query SQL HANA — allora sei un developer CDS senior. A quel punto il prossimo step non è leggere altro: è insegnare ad altri.

Esercizio del capitolo

Per ciascuna delle aree del capitolo, costruisci un piccolo proof of concept indipendente:

  1. Draft demo — entity Article con draft enabled. Custom handler che valida soft sul draft (lunghezza title) e strict all'activate (uniqueness). Verifica con due browser tab che il locking funziona.
  2. Event demo — service ShopService che emette OrderPlaced. Un secondo service InventoryService sottoscrive e decrementa lo stock. In-process prima, poi config Event Mesh.
  3. Multitenant demo — fai cds add multitenancy sul bookshop standard. Deploy su BTP trial. Onboarding di 2 tenant via API. Verifica che inserendo dati come tenant-A, tenant-B non li veda.
  4. Extension demo — sul progetto multitenant precedente, applica un'estensione che aggiunge campo customRating su Books solo per tenant-A. Verifica che tenant-B non veda il campo nel metadata.
  5. Performance audit — prendi un tuo progetto esistente, cerca 3 query con potenziale N+1. Riscrivile con expand. Misura il tempo prima/dopo con console.time.

Quando hai chiuso tutti e 5 i punti — complimenti. Sei expert. Adesso pensa al tuo progetto finale, perché il viaggio vero comincia adesso.
