Anatomia di un progetto CAP

Prima di scrivere una sola riga di CDS, vale la pena capire perché esiste, dove vive in un progetto, e che ruolo gioca rispetto a HANA e all'API OData. Questo capitolo è il fondamento: setup, struttura, e il modello mentale corretto.

Perché CDS esiste

CDS sta per Core Data Services. È un linguaggio dichiarativo creato da SAP per descrivere in un unico punto tre cose che, nello sviluppo tradizionale, vivono in posti separati: lo schema del database, il contratto di servizio esposto al client, e i metadata UI che pilotano il frontend.

Pensa a un'app classica enterprise. Hai uno schema SQL per il DB. Hai un controller REST o OData che definisce gli endpoint. Hai un'interfaccia che descrive quali campi mostrare, in che ordine, con che label. Tre artefatti, tre fonti di verità, tre opportunità di andare fuori sync.

CDS elimina questa frammentazione. Scrivi una sola volta com'è fatto un'entità, e il framework CAP (Cloud Application Programming Model) genera automaticamente tabelle HANA, endpoint OData V4, e — con le giuste annotation — anche la UI Fiori Elements.

Definizione operativa

CDS è il DNA dichiarativo di un'applicazione SAP moderna. Tutto il resto — handler in Node.js o Java, controller UI5, configurazione MTA — è impalcatura intorno al modello CDS.

Installare l'ambiente

Prerequisiti

Prima di scrivere una riga di CDS, ti servono tre cose installate localmente:

  • Node.js versione 20 o superiore. Verifica con node --version. È l'engine su cui gira CAP Node.js (esiste anche CAP Java, ma per il 90% dei progetti CAP Node.js è la scelta giusta).
  • Visual Studio Code con l'estensione SAP CDS Language Support. Senza l'estensione, ogni file .cds sembra un blob di testo nero su bianco; con l'estensione, hai syntax highlighting, auto-complete, jump-to-definition e validazione live.
  • Per il deploy su HANA Cloud, ti servirà anche Cloud Foundry CLI (cf) e l'estensione MBT (Multi-Target Application Build Tool): vedremo nel Capitolo 9.
terminal 
# Installa il CAP Development Kit globalmente
npm install -g @sap/cds-dk

# Verifica
cds --version

# Output atteso (versioni indicative):
# @sap/cds-dk: 8.x.x
# @sap/cds: 8.x.x
# Node.js: v20.x.x

I comandi essenziali

Il CLI cds è il tuo coltellino svizzero. Sono pochi comandi, ma li userai costantemente:

ComandoCosa fa
cds init nomeCrea un nuovo progetto CAP nella cartella nome/
cds watchAvvia il server in modalità development, ricarica su ogni modifica
cds compile file.cdsCompila un file CDS per ispezionarne l'output
cds deployEsegue il deploy su DB locale (SQLite di default)
cds buildPrepara i deliverable per il deploy produttivo (HANA)
cds add hanaAggiunge la configurazione per HANA Cloud al progetto
cds replApre una REPL interattiva — utilissima per testare query CQL

Il primo progetto

Crea il progetto, entra nella cartella, e diamo un'occhiata a cosa CAP ha scaffoldato per te:

terminal 
cds init bookshop
cd bookshop
ls -la

Struttura delle cartelle

Un progetto CAP appena creato ha questa anatomia:

filesystem 
bookshop/
├── app/                    # Frontend (UI5, Fiori Elements, HTML)
├── db/                     # Modello dati (schema)
│   └── schema.cds          # File principale del DB
├── srv/                    # Service layer
│   └── service.cds         # Definizione servizi OData
├── package.json            # Dipendenze e config CAP
├── .cdsrc.json             # Configurazione CDS (opzionale)
└── README.md

La regola d'oro: db/ per il modello dati, srv/ per i servizi, app/ per il frontend. CAP segue una convenzione "fortemente suggerita ma non obbligatoria": puoi mettere file .cds dove vuoi, ma se rispetti queste tre cartelle non devi configurare nulla — CAP li trova da solo.

Le convenzioni che contano

CAP è opinionated nel modo migliore: ti fa risparmiare configurazione se segui le sue convenzioni. Ecco le quattro più importanti:

  1. Namespace = path file. Un file in db/bookshop/schema.cds con namespace bookshop; diventa bookshop.NomeEntity nel mondo CDS.
  2. Auto-discovery. CAP scansiona db/ e srv/ all'avvio. Se il tuo file CDS è dentro queste cartelle, non devi importarlo manualmente.
  3. Entity plurali nei service. Un'entity Book diventa endpoint /Books. CAP pluralizza automaticamente (in inglese — per altre lingue puoi forzare con @cds.entity.name).
  4. OData V4 di default. Niente da configurare: appena definisci un service, è già esposto come OData V4 con tutte le sue capabilities ($filter, $expand, $count, ecc.).

Hello, CDS

Apri db/schema.cds (se non esiste, crealo) e scrivi:

db/schema.cds 
namespace my.bookshop;

entity Books {{
  key ID    : Integer;
  title     : String(100);
  stock     : Integer;
}}

Poi srv/cat-service.cds:

srv/cat-service.cds 
using {{ my.bookshop as db }} from '../db/schema';

service CatalogService {{
  entity Books as projection on db.Books;
}}

Quattro righe per il modello, tre per il servizio. Questo è già un backend funzionante.

Il magico cds watch

Nella root del progetto, lancia:

terminal 
cds watch

Vedrai output simile a:

output 
[cds] - loaded model from 2 file(s):

  db/schema.cds
  srv/cat-service.cds

[cds] - connect to db > sqlite { url: ':memory:' }
[cds] - serving CatalogService { path: '/odata/v4/catalog' }

[cds] - server listening on { url: 'http://localhost:4004' }
[cds] - launched at 21/05/2026, 14:32:18, version: 8.x.x, in: 412ms
[cds] - [ terminate with ^C ]

Apri http://localhost:4004 nel browser. Hai una pagina indice con i link al tuo service. Clicca su /odata/v4/catalog → vedi il service document. Aggiungi /$metadata all'URL → vedi i metadata OData generati automaticamente da CDS.

Hot reload

cds watch ricarica automaticamente al salvataggio di qualsiasi file .cds o .js. Non devi mai riavviarlo. Quando aggiungi una entity nuova, in 2 secondi è già esposta.

Leggere i metadata

Aprendo http://localhost:4004/odata/v4/catalog/$metadata vedi qualcosa di simile a:

metadata XML 
<EntityType Name="Books">
  <Key>
    <PropertyRef Name="ID"/>
  </Key>
  <Property Name="ID" Type="Edm.Int32" Nullable="false"/>
  <Property Name="title" Type="Edm.String" MaxLength="100"/>
  <Property Name="stock" Type="Edm.Int32"/>
</EntityType>

Questa è la magia di CDS: tu hai scritto 4 righe di linguaggio dichiarativo, CAP ha generato schema HANA, endpoint OData, e questo contratto formale che qualsiasi client (UI5, React, Postman) può consumare.

Il modello mentale giusto

Prima di tuffarsi in syntax e tipi, fissa nella tua testa questi tre principi. Ti risparmieranno mesi di confusione.

Primo: CDS è un linguaggio di definizione, non di esecuzione. Non scrivi "fai questo, poi quello". Scrivi "questo è fatto così". Il framework si occupa del come. Se ti trovi a chiederti "come faccio a far succedere X in CDS?", probabilmente la risposta è: non si fa in CDS, si fa in un handler JS. CDS descrive, non comanda.

Secondo: il modello CDS è la fonte di verità. Tutto deriva da lì: lo schema DB è generato dal modello, l'API OData è generata dal modello, la UI Fiori Elements (con le annotation) è generata dal modello. Se modifichi a mano il DB o l'API senza toccare il modello CDS, hai introdotto inconsistenza. Modifica sempre il .cds per primo.

Terzo: pensa per strati. Il modello in db/ descrive la persistenza. I service in srv/ sono proiezioni di quel modello, possibilmente filtrate e con permessi diversi. Lo stesso entity DB può apparire in due service diversi con shape diverso (uno completo per admin, uno ridotto per public). Questa stratificazione è il superpotere di CAP.

Errore tipico del principiante

Mettere logica di business dentro file CDS, o cercare di esporre direttamente le entity DB invece di farle passare attraverso una projection. Tieni sempre db/ 'pulito' (solo struttura dati), e fai tutta l'esposizione e la logica in srv/.

Esercizio del capitolo

Prima di passare al Capitolo 2, fai questo esercizio. Dovrebbe prenderti 15-20 minuti:

  1. Crea un progetto cds init library-mvp
  2. In db/schema.cds, definisci due entity: Book (ID, title, isbn, year) e Author (ID, firstName, lastName)
  3. In srv/library-service.cds, esponi entrambe come projection
  4. Lancia cds watch e verifica che gli endpoint OData siano attivi
  5. Apri il file $metadata nel browser e confronta cosa CAP ha generato con quello che hai scritto
  6. Bonus: usa POST da Postman o curl per creare un libro, poi GET per leggerlo

Se completi questo esercizio, hai compreso il ciclo base di CAP: scrivi CDS → CAP lo trasforma in DB + API in tempo reale. Da qui in poi, tutto il resto sono dettagli sopra questa fondamenta.
