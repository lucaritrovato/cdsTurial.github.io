Capitolo 06 · Services, actions, functions

Services, actions, functions

Il service è il punto in cui il tuo modello dati incontra il mondo. Qui decidi cosa esporre, a chi, come, e con quali regole. Più di tutto: definisci le operazioni — action e function — che sono il vero linguaggio di business della tua app.

Cos'è un service in CAP

Un service in CAP è il contratto tra il tuo modello dati e il mondo esterno. Nel layer db/ hai definito cosa sai (entity, association, view). Nel layer srv/ decidi cosa esponi, a chi, come. CAP traduce automaticamente ogni service in un endpoint OData V4 — completo di $metadata, query options, batching, ETag, draft handling, paginazione.

Una entity nel db è un'astrazione persistita; una entity in un service è una proiezione di quell'astrazione filtrata, rinominata, ristretta, calcolata. Lo stesso modello dati può sostenere decine di servizi diversi: uno per i clienti, uno per il backoffice, uno per il sistema partner B2B, ognuno con permessi, annotazioni UI e logica propria.

Mental model

Pensa a srv/ come al «cuoco di sala»: prende dalla cucina (db) gli ingredienti e li compone in piatti diversi per tavoli diversi. Il cosa sta in cucina; il per chi e come stanno in sala.

Esporre entity: projection, readonly, insertonly

La sintassi base per pubblicare una entity è la projection:

srv/catalog-service.cds 
using { sap.capire.bookshop as db } from '../db/schema';

service CatalogService {
  entity Books   as projection on db.Books;
  entity Authors as projection on db.Authors;
}

Per default ogni entity esposta è full CRUD. Ma raramente è quello che vuoi davvero. CAP offre annotazioni dichiarative per ridurre la superficie di attacco:

srv/catalog-service.cds 
service CatalogService {

  @readonly
  entity Books    as projection on db.Books;

  @insertonly
  entity Orders   as projection on db.Orders;

  entity Reviews  as projection on db.Reviews;
}

@readonly blocca CREATE, UPDATE, DELETE: l'entity è solo consultabile. @insertonly permette solo CREATE: utile per ordini, log, feedback — cose che si scrivono ma non si modificano. Senza annotazioni, è full CRUD.

Errore tipico

Esporre l'entity Users direttamente senza @restrict o senza una projection filtrata. Risultato: chiunque autenticato vede tutti gli utenti. La regola è: una projection per ogni audience.

Anatomia di una projection di servizio

Una projection in service è molto più di una copia. Puoi filtrare colonne, aggiungere calculated, rinominare, filtrare righe, nidificare association:

srv/catalog-service.cds 
service CatalogService {

  entity Books as select from db.Books {
    ID,
    title,
    price,
    stock,
    author.name as authorName,           // path expression
    price * 1.22 as priceWithVat : Decimal(9,2),  // calculated
    case when stock = 0 then 'out'
         when stock < 10 then 'low'
         else 'ok' end as stockStatus : String
  } where stock >= 0;                          // row filter

  entity PublicBooks as projection on db.Books
    excluding { createdBy, modifiedBy, cost };  // nascondi campi sensibili
}

L'espressione as projection on con excluding è il pattern più rapido per «tutto tranne X». L'espressione as select from dà controllo totale. Internamente è la stessa cosa: la projection diventa una view OData con regole proprie.

Pattern: layered services

Per applicazioni grandi, crea uno strato di servizio interno (es. InternalService) con tutta la logica, e poi servizi esterni che proiettano da quello. Il vantaggio: la logica vive in un solo posto, le projection di facciata sono leggere.

Path del servizio e @path

Per default CAP costruisce il path dell'endpoint partendo dal nome del servizio: CatalogService diventa /odata/v4/catalog/. Puoi sovrascrivere esplicitamente:

annotazione service 
@path: '/api/v2/catalog'
@(requires: 'authenticated-user')
service CatalogService {
  ...
}

Una buona pratica è versionare i servizi pubblici: /api/v1/..., /api/v2/.... Cambi breaking? Nuova versione, vecchia in deprecation. CAP non te lo impone, ma ti dà gli strumenti per farlo pulitamente.

package.json (estratto) 
# package.json - configurazione cds
"cds": {
  "requires": {
    "auth": "mocked",
    "db": "sqlite"
  },
  "odata": {
    "version": "v4",
    "flavor": "x4"
  }
}

Actions vs Functions: la differenza che ti farà sbagliare

Qui CAP eredita la terminologia OData e va presa sul serio:

  • Function — operazione idempotente, senza side-effect. Si invoca con GET. Esempi: calcolare uno sconto, restituire una classifica, validare un codice.
  • Action — operazione che cambia stato. Si invoca con POST. Esempi: confermare un ordine, approvare un documento, inviare una mail.

Sbagliare la categoria significa rompere il contratto HTTP. Un'action chiamata in GET sarà cacheata dal browser e dai proxy con effetti devastanti; una function chiamata in POST passerà revisioni di sicurezza come «operazione mutante» senza esserlo.

srv/catalog-service.cds 
service CatalogService {

  // FUNCTION: read-only, idempotente
  function getTopBooks(limit: Integer) returns array of Books;
  function calculateShipping(weight: Decimal, country: String) returns Decimal;

  // ACTION: muta stato
  action   submitOrder(book: UUID, quantity: Integer) returns Orders;
  action   resetCatalog();
}
Test rapido

Se chiamare l'operazione due volte produce due risultati diversi (un nuovo ordine, un'altra mail inviata), è una action. Se produce sempre lo stesso risultato, è una function.

Unbound actions e functions

Le operazioni unbound vivono al livello del servizio, non legate ad una entity specifica. Si chiamano via URL piatti come /catalog/getTopBooks(limit=10) o POST /catalog/submitOrder.

srv/catalog-service.cds 
service CatalogService {

  function searchBooks(
    query: String,
    minPrice: Decimal @mandatory,
    maxPrice: Decimal
  ) returns array of Books;

  action importCatalog(
    source: String,
    options: {
      overwrite : Boolean;
      dryRun    : Boolean;
    }
  ) returns {
    imported : Integer;
    skipped  : Integer;
    errors   : array of String;
  };
}

Nota i parametri strutturati e i tipi di ritorno strutturati anonimi: CAP supporta tutto, e le UI generate (Fiori Elements) sanno renderli come dialog form.

chiamate HTTP 
# Function: GET con parametri inline
GET /odata/v4/catalog/searchBooks(query='cap',minPrice=10,maxPrice=50)

# Action: POST con body JSON
POST /odata/v4/catalog/importCatalog
Content-Type: application/json

{
  "source": "s3://bucket/catalog.json",
  "options": { "overwrite": false, "dryRun": true }
}

Bound actions: l'arma più potente

Le operazioni bound sono legate ad una entity (o ad una sua collezione). Sono il modo idiomatico di esprimere «cose che si fanno a un record»: approvare, archiviare, inviare, duplicare, calcolare. L'URL diventa parlante e i client (Fiori Elements per primo) le rendono automaticamente come bottoni context-aware.

srv/catalog-service.cds 
service CatalogService {

  entity Books as projection on db.Books actions {

    // bound action su singolo record
    action discount(percent: Integer) returns Books;
    action archive();
    action duplicate() returns Books;

    // bound function
    function isAvailable() returns Boolean;
    function recommendations(limit: Integer) returns array of Books;
  };

  entity Orders as projection on db.Orders actions {
    action confirm() returns Orders;
    action cancel(reason: String);
    action refund(amount: Decimal) returns Orders;
  };
}

Gli URL diventano espliciti e gerarchici:

URL pattern bound 
# bound su singolo record (la key è nell'URL)
POST /odata/v4/catalog/Books(guid'a1b2-...')/CatalogService.discount
{ "percent": 15 }

# bound function
GET /odata/v4/catalog/Books(guid'a1b2-...')/CatalogService.isAvailable()

# bound su un Order
POST /odata/v4/catalog/Orders(guid'c3d4-...')/CatalogService.cancel
{ "reason": "customer request" }
Come scegliere

Bound quando l'operazione ha senso solo nel contesto di un record specifico (cancella questo ordine). Unbound quando opera su molti record, su una collezione, o non ha un soggetto chiaro (importa il catalogo, cerca).

Tipi di ritorno: scalare, entity, array

Le action e function possono restituire qualsiasi cosa: tipi primitivi, entity intere, array di entity, strutture anonime, oppure niente (void).

srv/catalog-service.cds 
service CatalogService {

  // ritorno scalare
  function countBooks() returns Integer;
  function getVersion() returns String;

  // ritorno entity intera
  function findBook(isbn: String) returns Books;

  // ritorno array
  function topBooks(limit: Integer) returns array of Books;

  // ritorno strutturato anonimo
  function stats() returns {
    totalBooks  : Integer;
    avgPrice    : Decimal(9,2);
    topAuthor   : String;
    byCategory  : array of {
      category : String;
      count    : Integer;
    };
  };

  // nessun ritorno
  action notify(message: String);
}
Tipi anonimi: usali con misura

Comodi sì, ma se la stessa struttura compare in più posti, definisci un type esplicito. Le UI generate (Fiori Elements) hanno più materiale su cui lavorare e la documentazione del servizio risulta più leggibile.

Tipi nominati:

tipi riutilizzabili 
type CatalogStats {
  totalBooks : Integer;
  avgPrice   : Decimal(9,2);
  topAuthor  : String;
}

service CatalogService {
  function stats() returns CatalogStats;
}

Custom handlers: before, on, after

Fin qui hai modellato. Ora dai vita al servizio con codice. CAP usa il pattern event-driven handler: tu registri funzioni che reagiscono a eventi sul servizio. Tre fasi, tre intenti:

  • before — validazione, autorizzazione, modifica del payload prima della persistenza.
  • on — sostituisci l'implementazione default (raro per CRUD, frequente per action/function).
  • after — arricchimento dei risultati, logging, notifiche dopo la transazione.
srv/catalog-service.js 
// srv/catalog-service.js
const cds = require('@sap/cds');

module.exports = cds.service.impl(async function () {
  const { Books, Orders } = this.entities;

  // BEFORE: validazione
  this.before('CREATE', Books, req => {
    if (req.data.price < 0) {
      req.error(400, 'Price must be positive', 'price');
    }
    if (!req.data.title?.trim()) {
      req.error(400, 'Title required', 'title');
    }
  });

  // BEFORE su UPDATE: solo l'autore può modificare i propri libri
  this.before('UPDATE', Books, async req => {
    const book = await SELECT.one.from(Books).where({ ID: req.data.ID });
    if (book.createdBy !== req.user.id) req.reject(403);
  });

  // ON: implementazione di un'action
  this.on('submitOrder', async req => {
    const { book, quantity } = req.data;
    const b = await SELECT.one.from(Books).where({ ID: book });
    if (!b || b.stock < quantity) req.reject(409, 'Insufficient stock');

    await UPDATE(Books).set({ stock: { '-=': quantity } }).where({ ID: book });
    return INSERT.into(Orders).entries({ book_ID: book, quantity });
  });

  // AFTER: arricchimento dati
  this.after('READ', Books, books => {
    for (const b of books) {
      b.discount = b.price > 50 ? '10% off' : null;
    }
  });

  // AFTER: side-effect (notifica)
  this.after('CREATE', Orders, async order => {
    await this.emit('OrderCreated', { id: order.ID, total: order.total });
  });
});
Pattern: handler in file separati

Per servizi grossi, dividi gli handler per entity in file dedicati e importali nel file principale. srv/handlers/books.js, srv/handlers/orders.js, ecc. Mantiene basso il rumore e facile la code review.

req, error, reject: gestire i fallimenti

L'oggetto req è il tuo amico in ogni handler. Espone req.data, req.user, req.query, req.params, req.locale, e i metodi req.error(), req.reject(), req.info(), req.warn().

validation pattern 
this.before('CREATE', Books, req => {

  // error: aggiunge errore alla risposta MA continua a raccogliere altri errori
  if (!req.data.title)  req.error(400, 'Title required', 'in/title');
  if (req.data.price < 0) req.error(400, 'Price >= 0', 'in/price');
  // risultato: payload con MULTIPLI errori (ottimo per form validation)

  // reject: interrompe SUBITO con un solo errore
  if (req.user.id === 'anonymous') req.reject(401, 'Login required');

  // info / warn: messaggi informativi nella risposta, non bloccanti
  if (req.data.stock > 10000) req.warn('Stock molto alto');
});
Sicurezza

Mai esporre messaggi di errore con dettagli tecnici (stack trace, SQL, path file). Usa codici di errore generici per il client e logga i dettagli sul server con cds.log. CAP per default mappa le eccezioni non gestite a 500 Internal Server Error, ma controlla sempre cosa esce.

Multi-service e composizione

Una applicazione CAP reale espone più servizi. È normale e desiderabile:

due servizi, stessa base 
// srv/catalog-service.cds — per i clienti finali
service CatalogService @(path: '/catalog') {
  @readonly entity Books   as projection on db.Books;
  @readonly entity Authors as projection on db.Authors;
  action submitOrder(book: UUID, quantity: Integer);
}

// srv/admin-service.cds — backoffice, autenticato
@(requires: 'admin')
service AdminService @(path: '/admin') {
  entity Books   as projection on db.Books;
  entity Orders  as projection on db.Orders;
  entity Authors as projection on db.Authors;
}

I servizi si possono chiamare tra loro via cds.connect.to():

service composition 
// in un handler di AdminService
const catalog = await cds.connect.to('CatalogService');
const topBooks = await catalog.run(SELECT.from('Books').limit(10));

// chiamare un servizio esterno (es. SAP S/4HANA via destination)
const s4 = await cds.connect.to('API_BUSINESS_PARTNER');
const partners = await s4.run(SELECT.from('A_BusinessPartner').where({ Country: 'IT' }));
Pattern: BFF (Backend For Frontend)

Crea un service sottile per ogni client (web, mobile, B2B partner). Ogni BFF aggrega chiamate ai servizi «core» e le presenta nel formato giusto per quel client. CAP rende questo pattern naturale: i BFF sono solo file .cds con projection e handler che orchestrano.

Esercizio del capitolo

Progetta un service BookshopService per una libreria online:

  1. Catalogo pubblico (no auth) — @readonly su Books, Authors, Categories.
  2. Action submitOrder (unbound, autenticata) — valida stock, scala disponibilità, crea Order, emette evento OrderPlaced.
  3. Function recommendBooks (bound a Books) — restituisce 5 libri della stessa categoria, ordinati per rating.
  4. Bound action cancel su Order — ripristina lo stock e marca l'ordine come CANCELLED.
  5. Bound function history su Authors — restituisce gli ultimi 10 libri pubblicati dall'autore.
  6. Handler before('CREATE', Books) che valida ISBN, formato e stock minimo.
  7. Handler after('READ', Books) che aggiunge campo onSale calcolato.
Bonus expert

Crea un secondo service AdminBookshopService riservato al ruolo admin, che espone le stesse entity ma full CRUD, più un'action importFromCSV con parametro stream.
