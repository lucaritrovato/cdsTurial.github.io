Capitolo 02 · Sintassi, tipi, entity

Sintassi, tipi, entity

Il vocabolario di base del linguaggio CDS. Tipi primitivi, chiavi, constraints, default, tipi strutturati, enum. E soprattutto: come ogni costrutto CDS viene tradotto in DDL HANA reale al deploy.

Anatomia di un'entity

Un'entity in CDS è la dichiarazione di una "tabella logica" — anche se vedremo che può finire come tabella reale, view, o nient'affatto sul DB. La sintassi minima è semplice:

struttura base 
entity NomeEntity {{
  key nomeChiave : Tipo;
  nomeCampo1      : Tipo;
  nomeCampo2      : Tipo not null;
  nomeCampo3      : Tipo default 'valore';
}}

Ogni dichiarazione di campo è una riga con tre parti: nome, due punti, tipo, e zero o più modificatori (key, not null, default, ecc.). Il punto e virgola finale è obbligatorio.

Convenzioni di naming

Le entity in CAP si scrivono in PascalCase plurale (Books, Orders, CustomerProfiles). I campi in camelCase (firstName, totalPrice). Non è obbligatorio, ma se segui questa convenzione il tuo codice si integra naturalmente con tutto l'ecosistema SAP.

I tipi primitivi

CDS definisce un set di tipi astratti che vengono poi mappati al tipo nativo del database target. Lo stesso modello CDS funziona su HANA, SQLite, PostgreSQL — il framework si occupa del mapping.

Stringhe

cds 
entity TextExamples {{
  shortText     : String(50);        // stringa con lunghezza max
  defaultString : String;            // max 5000 char di default
  longText      : LargeString;       // NCLOB su HANA, illimitato
  binaryData    : Binary(200);        // BLOB con max length
  bigBlob       : LargeBinary;       // BLOB illimitato
}}

Su HANA, String(n) diventa NVARCHAR(n) (Unicode-safe, raccomandato). LargeString diventa NCLOB. Se non specifichi la lunghezza, CAP usa 5000 come default — abbastanza per la maggior parte dei testi liberi, ma specifica sempre una lunghezza ragionevole: aiuta il DB a ottimizzare e ti costringe a pensare ai limiti.

Numeri

cds 
entity NumericExamples {{
  count        : Integer;            // INT (32-bit)
  bigCount     : Integer64;          // BIGINT (64-bit)
  microCount   : UInt8;              // 0-255, ottimo per status flags
  smallCount   : Int16;              // -32k a +32k
  
  price        : Decimal(9,2);         // 9 cifre totali, 2 decimali
  preciseValue : Decimal(31,10);       // alta precisione
  ratio        : Decimal;             // precision dinamica
  
  ratingFloat  : Double;             // IEEE 754 double
}}
Decimal vs Double

Per soldi, quantità, percentuali, usa SEMPRE Decimal, mai Double. Double è floating point e introduce errori di arrotondamento. Decimal(9,2) garantisce precisione esatta: 9 cifre totali, di cui 2 dopo la virgola, quindi max 9999999.99.

Date e tempo

cds 
entity DateExamples {{
  birthDate    : Date;              // solo data: 2025-12-31
  startTime    : Time;              // solo ora: 14:30:00
  createdAt    : DateTime;          // data+ora, precisione al secondo
  modifiedAt   : Timestamp;         // data+ora con frazioni di secondo, UTC
}}

La regola pratica: per timestamp di sistema (createdAt, modifiedAt) usa Timestamp. Per date di business (nascita, scadenza) usa Date. DateTime ha precisione al secondo e va bene per appuntamenti o eventi non ad alta frequenza.

Tipi speciali

cds 
entity SpecialExamples {{
  uuid         : UUID;              // String(36) auto-generato
  isActive     : Boolean;           // true/false
  rawValue     : Binary(16);         // byte array
}}

UUID è in realtà una String(36) con superpoteri: CAP la genera automaticamente come chiave primaria se la dichiari come key ID : UUID;. Su HANA diventa NVARCHAR(36). È il tipo di chiave raccomandato per qualsiasi modello moderno: niente sequenze gestite dal DB, niente collisioni, distributable across systems.

Chiavi primarie

In CDS si dichiarano col modificatore key davanti al nome del campo:

cds 
entity Books {{
  key ID    : UUID;          // chiave singola, raccomandato
  title     : String;
}}

// Chiave composta:
entity BookCategories {{
  key book     : UUID;
  key category : String(10);
  weight       : Decimal(3,2);
}}

Tre regole sulle chiavi:

  1. Ogni entity persistita deve avere almeno una chiave. Se manchi, cds compile dà errore.
  2. Le chiavi sono implicitamente not null. Non serve scriverlo.
  3. UUID si auto-genera per POST via OData, sempre che la dichiari come key ID : UUID;. Se la chiave è di altro tipo (Integer, String), devi fornirla esplicitamente nel payload.

Constraints e default

Not null e obbligatorietà

cds 
entity Books {{
  key ID : UUID;
  title  : String not null;       // vincolo DB
  author : String @mandatory;       // vincolo applicativo
  notes  : String;                  // opzionale
}}

Attenzione alla sfumatura: not null e @mandatory non sono la stessa cosa.

  • not null è un vincolo a livello di database: se provi a salvare un record senza quel valore, il DB rifiuta con un errore SQL.
  • @mandatory è un'annotation OData: il client OData/UI5 saprà che il campo è obbligatorio (mostra asterisco rosso, valida prima di inviare), ma se bypassi il client il DB accetta il null.
  • Spesso si usano insieme: not null per la sicurezza del dato, @mandatory per la UX.

Valori di default

cds 
entity Orders {{
  key ID    : UUID;
  status    : String(10) default 'draft';
  quantity  : Integer    default 1;
  isPaid    : Boolean    default false;
  createdAt : Timestamp  default $now;
  createdBy : String     default $user;
}}

I default vengono applicati lato DB (per chi crea record bypassando l'API) e anche dal runtime CAP. $now e $user sono magic variables: vengono risolte dal framework rispettivamente come timestamp corrente e ID utente autenticato. Vedremo nel Capitolo 4 che esistono aspect predefiniti (managed) che gestiscono questi default in modo standard.

Tipi strutturati

Puoi raggruppare campi correlati in strutture annidate. Su HANA queste strutture diventano colonne con nome composto (address_street, address_city), ma nel modello e nell'API restano nested:

cds 
entity Customers {{
  key ID   : UUID;
  name     : String;
  
  address : {{
    street : String;
    city   : String;
    zip    : String(10);
    country: String(2);
  }};
  
  contacts : {{
    email : String;
    phone : String;
  }};
}}

Vantaggi: la API OData espone customer.address.city come oggetto annidato (più pulito per il client), e nel DB le colonne sono raggruppate logicamente. Svantaggio: non puoi indicizzare individualmente sotto-campi in tutti i casi. Usali per dati coesi (indirizzi, contatti, money), non come gerarchia profonda.

Type aliases

Riutilizza definizioni di tipo per consistenza:

cds 
type Currency     : String(3);
type EmailAddress : String(255);
type Money        : Decimal(15,2);

entity Invoices {{
  key ID  : UUID;
  amount  : Money;
  currency: Currency;
  contact : EmailAddress;
}}

Pattern d'oro: definisci i type alias in un file db/common.cds e fai using in tutto il progetto. Quando un giorno dovrai cambiare Money da Decimal(15,2) a Decimal(19,4), lo cambi in un posto solo.

Enumerazioni

CDS supporta enum inline o come tipo separato:

cds 
// Enum inline
entity Orders {{
  key ID : UUID;
  status : String enum {{
    draft;
    submitted;
    approved;
    rejected;
    shipped;
  }};
}}

// Enum come type riusabile
type Priority : Integer enum {{
  low    = 1;
  medium = 2;
  high   = 3;
}}

entity Tickets {{
  key ID  : UUID;
  priority : Priority;
}}

Gli enum diventano vincoli CHECK su HANA, e nei metadata OData diventano EnumType che il client può usare per popolare dropdown automaticamente. In più, l'estensione CDS di VS Code ti dà autocompletamento sui valori.

Esercizio del capitolo

Modella un'entity Employee che includa:

  • Chiave UUID
  • Nome e cognome (max 50 char ciascuno, obbligatori a livello DB)
  • Email obbligatoria solo lato applicativo (usa @mandatory)
  • Stipendio con precisione monetaria (usa un type alias Money)
  • Data di assunzione (default = oggi)
  • Ruolo come enum (junior, mid, senior, lead)
  • Indirizzo come struttura annidata (via, città, CAP, paese)
  • Flag isActive con default true
  • Timestamp di creazione (default $now)

Lancia cds watch, apri $metadata e verifica che tutto sia mappato correttamente in OData. Poi, prova ad eseguire cds compile db/schema.cds --to sql per vedere lo schema HANA SQL generato.
