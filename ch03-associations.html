Capitolo 03 · Associations & Compositions

Associations & Compositions

Il cuore del modello dati relazionale in CDS. Capire profondamente la differenza tra Association e Composition è il singolo skill più importante per modellare correttamente in CAP — più di qualsiasi conoscenza di sintassi.

Association vs Composition

Questo capitolo affronta una delle distinzioni più importanti — e più fraintese — di CDS. La differenza tra Association e Composition non è sintattica, è semantica, e cambia profondamente il comportamento runtime di CAP.

In una frase: una Composition è una relazione padre-figlio in cui i figli non hanno vita propria. Una Association è invece un puntatore a un'entità indipendente.

AspettoAssociationComposition
Vita del targetIndipendenteVincolata al padre
Cancellazione padreTarget sopravviveTarget eliminato (cascade)
EsempioBook → AuthorOrder → OrderItems
Deep insert in APISolo per draftSì, di default
Draft con @odata.draft.enabledNon incluso nel draftIncluso nel draft
Esposizione separataSì, entity propriaSolitamente no
La domanda da farsi

Se il record figlio esiste anche senza il padre, è Association. Se non ha senso da solo (un "OrderItem" senza ordine, una "Review" senza il prodotto recensito), è Composition.

Association di base

Association to one

La forma più comune: un libro punta a un autore.

cds 
entity Authors {{
  key ID : UUID;
  name   : String;
}}

entity Books {{
  key ID : UUID;
  title  : String;
  author : Association to Authors;
}}

Cosa succede dietro le quinte? CAP aggiunge automaticamente alla tabella Books una colonna author_ID (foreign key verso Authors.ID). Nel JSON OData ricevi qualcosa come:

GET /Books(abc-123) 
{{
  "ID": "abc-123",
  "title": "Il nome della rosa",
  "author_ID": "def-456"
}}

E con $expand=author:

GET /Books(abc-123)?$expand=author 
{{
  "ID": "abc-123",
  "title": "Il nome della rosa",
  "author": {{
    "ID": "def-456",
    "name": "Umberto Eco"
  }}
}}

Association to many

Il lato opposto: un autore con molti libri. Qui c'è una sottigliezza importante.

cds 
entity Authors {{
  key ID : UUID;
  name   : String;
  books  : Association to many Books 
             on books.author = $self;
}}

Le Association to many non hanno una foreign key — non possono averla, dato che la relazione "uno-a-molti" sta sul lato "molti". CAP risolve l'associazione tramite la clausola on, che dice: "i libri di questo autore sono quelli in cui books.author punta a me ($self)".

La variabile $self rappresenta "l'istanza corrente di Authors". È equivalente al this dei linguaggi a oggetti.

Managed associations

Una Association to one senza on clause è detta managed: CAP gestisce automaticamente la foreign key. Sono le più comode e le più usate. Ne hai già visto un esempio sopra:

cds 
author : Association to Authors;
// equivalente a: author : Association to Authors on author.ID = author_ID;
// CAP genera silenziosamente la colonna author_ID

Se la chiave target è composta (più di un campo), CAP genera multiple FK columns con suffissi appropriati.

Unmanaged: ON clause

A volte serve modellare relazioni più complesse, dove la FK è una colonna esistente che non è la chiave standard:

cds 
entity Books {{
  key ID  : UUID;
  isbn    : String(13);
  
  // FK custom: collega tramite isbn invece di ID
  edizione : Association to Edizioni  
             on edizione.isbn = isbn;
}}
Quando NON usare unmanaged

Le association unmanaged sono utili ma fragili. Se modifichi il nome del campo a sinistra o destra dell'on, devi aggiornare l'on. Preferisci sempre le managed quando puoi.

Composition

Sintatticamente quasi identica alle association, ma cambia il comportamento runtime.

Composition di figli

cds 
entity Orders {{
  key ID : UUID;
  customer : String;
  
  items : Composition of many OrderItems 
            on items.order = $self;
}}

entity OrderItems {{
  key ID : UUID;
  order    : Association to Orders;
  product  : String;
  quantity : Integer;
}}

Tre comportamenti automatici scattano grazie alla parola Composition:

  1. Cascade delete: cancellare un Order elimina automaticamente i suoi OrderItems
  2. Deep insert nativo: puoi creare ordine + righe in una sola POST
  3. Draft inclusion: se Order ha @odata.draft.enabled, anche OrderItems entrano nello stesso draft

Esempio di deep insert in OData:

JSON 
POST /Orders
{{
  "customer": "Mario Rossi",
  "items": [
    {{ "product": "Libro A", "quantity": 2 }},
    {{ "product": "Libro B", "quantity": 1 }}
  ]
}}

CAP crea Order e i due OrderItems in una transazione atomica. Con una semplice Association questo non sarebbe possibile out-of-the-box.

Il backlink

Hai notato che OrderItems ha order : Association to Orders? Questo è il backlink: il "ritorno" dal figlio al padre. È un'Association normale (non Composition!), perché OrderItems punta al padre, non lo possiede.

Da qualche versione di CAP, puoi usare una sintassi più concisa con aspect bidirezionale:

cds 
entity Orders {{
  key ID : UUID;
  items : Composition of many {{
    key pos : Integer;
    product  : String;
    quantity : Integer;
  }};
}}

Qui CAP definisce automaticamente l'entity figlia inline, con chiave composta (Order's ID + pos). Pulito per child entity che non vengono esposte separatamente.

Self-references

Una entity può puntare a se stessa — utile per gerarchie (categorie con sotto-categorie, dipendenti con manager, ecc.):

cds 
entity Categories {{
  key ID : UUID;
  name     : String;
  
  parent   : Association to Categories;
  children : Composition of many Categories 
               on children.parent = $self;
}}

Nota un dettaglio: parent è un'Association (le categorie radice possono esistere senza parent), children è una Composition (se cancelli una categoria, le sue figlie spariscono — comportamento di solito desiderato per gerarchie).

Many-to-many

CDS non ha un costrutto nativo per N:M — devi modellare la tabella di link esplicitamente. Pattern standard:

cds 
entity Books {{
  key ID : UUID;
  title  : String;
  genres : Composition of many Book2Genre 
             on genres.book = $self;
}}

entity Genres {{
  key code : String(20);
  name     : String;
  books    : Association to many Book2Genre 
               on books.genre = $self;
}}

entity Book2Genre {{
  key book  : Association to Books;
  key genre : Association to Genres;
}}

Tre osservazioni: la link table Book2Genre ha chiave composta dai due lati; il lato Books.genres è una Composition (i link "appartengono" al libro); il lato Genres.books è una semplice Association to many (i generi esistono indipendentemente).

Se hai bisogno di attributi sulla relazione (es. priorità del genere, da quando un libro è associato a un genere), aggiungi campi alla link table.

Cascade e referential integrity

Per default CAP genera CHECK e foreign key constraints su HANA che impediscono associazioni orfane. Comportamento di default:

OperazioneAssociationComposition
DELETE padre con figli esistentiErrore FK violationCascade delete dei figli
UPDATE FK con target inesistenteErrore FK violationErrore FK violation
INSERT figlio senza padreErrore FK violationErrore FK violation

Puoi disabilitare/personalizzare con annotation:

cds 
entity Books {{
  key ID : UUID;
  
  @assert.integrity: false  // nessun FK constraint generato
  author : Association to Authors;
}}
Sconsigliato in produzione

Disabilitare i constraint può sembrare comodo per evitare errori durante il dev, ma in produzione apre la porta a dati corrotti. Mantieni i constraint attivi e gestisci correttamente le cancellazioni a livello di business logic.

Anti-pattern da evitare

Errori frequenti che vedo in code review di progetti CAP:

1. Usare Association quando serve Composition. Se vedi che ogni volta che cancelli un padre devi anche cancellare manualmente i figli con un handler before DELETE, hai sbagliato: doveva essere una Composition.

2. Usare Composition quando serve Association. Se hai dichiarato Composition of many Reviews ma poi vuoi esporre le Reviews come endpoint indipendente con il loro service, è meglio una Association.

3. Dimenticare il backlink. Una Composition of many richiede sempre un'Association di ritorno sul figlio. Senza, CAP non sa come collegare i record.

4. Composition annidate troppo profonde. Più di 3 livelli di Composition (es. Order → Items → SubItems → Variants) diventa difficile da gestire, soprattutto con i draft. Considera di "appiattire" con association.

5. Many-to-many senza link table esplicita. Non esiste sintassi tipo "Books.genres : Many to Genres". Devi sempre passare per una link entity.

Esercizio del capitolo

Modella un sistema "Conference Management". Entity richieste:

  • Conferences: ID, title, date, location, sessions (Composition of many Sessions)
  • Sessions: ID, title, conference (backlink), speaker (Association to Speakers), attendees (many-to-many con Attendees, con un campo registeredAt)
  • Speakers: ID, name, bio
  • Attendees: ID, name, email
  • Tracks: gerarchica con self-reference (track padre opzionale)

Verifica con cds compile che lo schema generato sia coerente. Poi prova un deep insert via OData per creare una Conference con due Sessions, ognuna con uno Speaker e due Attendees.
