Capitolo 09 · Deploy & HANA nativo

Deploy & HANA nativo

Tutto quello che hai imparato funziona in locale con SQLite. Il momento della verità arriva con HANA Cloud: HDI, MTA, artefatti generati, native artifacts. Capirne il funzionamento ti separa dal «developer CAP» al cloud engineer SAP.

Dal locale a HANA Cloud: il salto

Durante lo sviluppo userai SQLite in-memory o file: si avvia in millisecondi, non richiede configurazione, è perfetto per il loop interno di cds watch. Ma il momento in cui deployi su BTP, ti aspetta SAP HANA Cloud — un database completamente diverso, con caratteristiche, sintassi avanzata, e tooling propri.

CAP fa di tutto per nasconderti la differenza: il 95% del codice gira identico su SQLite e HANA. Ma quel 5% — tipi nativi HANA, view di calculation, procedure, partitioning, sequence — è spesso il punto in cui un'app passa da «funziona» a «funziona in produzione».

Strategia di studio

Inizia tutti i progetti con SQLite per velocità di iterazione. Aggiungi HANA quando il modello dati è stabile. Mai sviluppare direttamente in HANA: i cicli di feedback sarebbero troppo lenti.

cds add hana e la configurazione

comandi base 
# aggiungi supporto HANA al progetto
cds add hana --for production

# aggiungi MTA descriptor (per Cloud Foundry deploy)
cds add mta

# prepara il build di produzione
cds build --production

Cosa fanno questi comandi:

  • cds add hana aggiorna package.json aggiungendo @sap/cds-hana e dichiarando db di tipo hana per il profilo production.
  • cds add mta crea il file mta.yaml che descrive l'applicazione come Multi-Target Application: moduli (db deployer, srv, app), risorse (HANA service, XSUAA, destination), dipendenze.
  • cds build --production compila il modello in gen/db/ producendo gli artefatti HDI che verranno effettivamente deployati.
config multi-profilo 
# estratto di package.json dopo cds add hana
"cds": {
  "requires": {
    "db": {
      "[development]": { "kind": "sqlite", "credentials": { "url": "db.sqlite" } },
      "[production]":  { "kind": "hana",   "deploy-format": "hdbtable" }
    }
  }
}

Il pattern dei profili è centrale: lo stesso package.json descrive sia il comportamento locale (SQLite) sia quello produttivo (HANA). Si attivano via NODE_ENV=production o cds.env.profiles.

HDI: cosa è e perché cambia tutto

HDI (HANA Deployment Infrastructure) è il sistema con cui HANA Cloud gestisce gli schemi. Non scrivi più CREATE TABLE a mano: tu fornisci file descrittivi (.hdbtable, .hdbview, .hdbprocedure, ...), HDI calcola il delta tra lo stato attuale e quello desiderato, applica le modifiche in modo idempotente e transazionale.

Concetti chiave:

  • HDI container = uno schema HANA isolato, con un suo set di privilegi. Tutti gli oggetti del tuo progetto vivono qui.
  • Design-time artifacts = file .hdb* nel filesystem. Non SQL, ma descrittori dichiarativi.
  • Runtime artifacts = oggetti HANA effettivi (tabelle, view, procedure). Generati da HDI a partire dai design-time.
  • HDI deployer = il modulo che legge i file e li applica al container.
Mental model HDI vs schema classico

HDI è come Git per il DB schema: ogni deploy è un commit dichiarativo, lo stato attuale è tracciato, i rollback sono fattibili. Lo schema classico HANA (CREATE TABLE imperativo) è come l'FTP: lo stato è quello che è e nessuno sa più cosa è successo.

cds build: anatomia degli artefatti generati

Dopo cds build --production trovi la cartella gen/db/ con questa struttura:

struttura gen/db/ 
gen/
└── db/
    ├── src/
    │   └── gen/
    │       ├── sap.capire.bookshop-Books.hdbtable
    │       ├── sap.capire.bookshop-Authors.hdbtable
    │       ├── sap.capire.bookshop-Reviews.hdbtable
    │       ├── CatalogService-Books.hdbview
    │       ├── CatalogService-Authors.hdbview
    │       ├── .hdiconfig
    │       └── .hdinamespace
    ├── package.json     # descrive il modulo deployer
    └── undeploy.json    # tracking di artefatti da rimuovere

Punti notevoli:

  • Le entity CDS diventano .hdbtable.
  • Le projection e view diventano .hdbview.
  • I service diventano view con il loro namespace (CatalogService-Books.hdbview).
  • I file .hdiconfig e .hdinamespace sono configurazione HDI (file engine mapping, namespacing).

.hdbtable, .hdbview, .hdbconstraint

Vediamo un .hdbtable generato (formato classico, dichiarativo):

hdbtable generato 
-- gen/db/src/gen/sap.capire.bookshop-Books.hdbtable
COLUMN TABLE "sap.capire.bookshop.Books" (
  "ID"            NVARCHAR(36) NOT NULL,
  "createdAt"     TIMESTAMP,
  "createdBy"     NVARCHAR(255),
  "modifiedAt"    TIMESTAMP,
  "modifiedBy"    NVARCHAR(255),
  "title"         NVARCHAR(100) NOT NULL,
  "price"         DECIMAL(9,2),
  "stock"         INTEGER DEFAULT 0,
  "author_ID"     NVARCHAR(36),
  PRIMARY KEY ("ID")
)
hdbview generato 
-- gen/db/src/gen/CatalogService-Books.hdbview
VIEW "CatalogService.Books" AS
SELECT
  Books_0."ID"          AS "ID",
  Books_0."title"       AS "title",
  Books_0."price"       AS "price",
  Authors_1."name"      AS "authorName"
FROM "sap.capire.bookshop.Books" Books_0
LEFT OUTER JOIN "sap.capire.bookshop.Authors" Authors_1
  ON Books_0."author_ID" = Authors_1."ID"
foreign key constraint 
-- gen/db/src/gen/sap.capire.bookshop-Books.author.hdbconstraint
CONSTRAINT "sap.capire.bookshop.Books.author"
  ON "sap.capire.bookshop.Books" ("author_ID")
  REFERENCES "sap.capire.bookshop.Authors" ("ID")
  ON UPDATE CASCADE
  ON DELETE RESTRICT
Mapping tipi CDS → HANA

CAP usa una mappatura precisa: String → NVARCHAR, Decimal(p,s) → DECIMAL(p,s), UUID → NVARCHAR(36), Boolean → BOOLEAN, LargeString → NCLOB, Binary → VARBINARY. Le date sono sempre TIMESTAMP con timezone UTC.

MTA: il deploy descriptor

Per deployare su BTP Cloud Foundry serve un mta.yaml che descriva l'app come Multi-Target Application. CAP lo genera con cds add mta:

mta.yaml 
# mta.yaml — versione semplificata
ID: bookshop
_schema-version: '3.3'
version: 1.0.0

modules:
  - name: bookshop-db-deployer
    type: hdb
    path: gen/db
    requires:
      - name: bookshop-db          # referenzia la risorsa HANA

  - name: bookshop-srv
    type: nodejs
    path: gen/srv
    requires:
      - name: bookshop-db
      - name: bookshop-auth
    provides:
      - name: srv-api
        properties: { srv-url: '${default-url}' }

  - name: bookshop-app
    type: html5
    path: gen/app

resources:
  - name: bookshop-db
    type: com.sap.xs.hdi-container       # HANA Cloud HDI container
    parameters:
      service: hana
      service-plan: hdi-shared

  - name: bookshop-auth
    type: org.cloudfoundry.managed-service
    parameters:
      service: xsuaa
      service-plan: application
      path: ./xs-security.json
build & deploy CF 
# build e deploy
mbt build                              # produce bookshop_1.0.0.mtar
cf deploy mta_archives/bookshop_1.0.0.mtar

Native artifacts: hdbprocedure, hdbcalculationview

CAP non è in conflitto con HANA nativo: lo integra. Puoi mettere file .hdbprocedure e .hdbcalculationview nella cartella db/src/ e CAP li includerà nel deploy.

stored procedure HANA 
-- db/src/calc_top_books.hdbprocedure
PROCEDURE "calc_top_books" (
  IN  category NVARCHAR(10),
  OUT result TABLE(book_id NVARCHAR(36), score DECIMAL(10,2))
)
LANGUAGE SQLSCRIPT
SQL SECURITY INVOKER
READS SQL DATA AS
BEGIN
  result =
    SELECT b."ID" AS book_id,
           (avg_rating * 0.6 + log(units_sold + 1) * 0.4) AS score
    FROM "sap.capire.bookshop.Books" b
    JOIN book_stats ON b."ID" = book_stats.book_id
    WHERE b."category_code" = :category
    ORDER BY score DESC
    LIMIT 20;
END
invocazione da CAP 
// chiamarla da un handler CAP
this.on('topBooks', async req => {
  const { category } = req.data;

  const sql = 'CALL "calc_top_books"(?, ?)';
  const result = await cds.db.run(sql, [category]);
  return result;
});

Per le calculation view grafiche (XML/JSON in .hdbcalculationview) il principio è lo stesso: file nel filesystem, deploy via HDI, esposizione opzionale tramite entity CDS con @cds.persistence.exists.

Quando passare al nativo

Restate in CDS finché potete. Passate al nativo quando: (a) avete logica analitica pesante con dimensioni e measure che richiedono calculation view, (b) avete logica algoritmica complessa che vale la pena spingere al DB (es. machine learning HANA), (c) integrate sistemi legacy con sinonimi su altri schemi.

@cds.persistence.exists / skip

Due annotation cruciali per dialogare con HANA nativo:

annotation persistence 
// la tabella ESISTE GIÀ (creata da hdbtable manuale, da legacy, da sinonimo)
// CAP non la crea, ma la usa come riferimento
@cds.persistence.exists
entity LegacyCustomers {
  key id   : String(10);
  name     : String(100);
  country  : String(2);
}

// non persistere: la entity vive solo nel modello (utile per type, view input/output)
@cds.persistence.skip
entity ComputedOnly {
  value : Decimal;
}

// referenzia una calculation view esistente
@cds.persistence.exists
entity SalesAnalytics {
  key period  : String;
  key country : String;
  revenue     : Decimal(15,2);
  units       : Integer;
}
Pattern: HANA-first

In molti progetti SAP esiste già uno schema HANA con tabelle storiche. La strategia idiomatica: dichiarare le tabelle esistenti come entity @cds.persistence.exists, costruirci sopra view CDS e service. CAP diventa il linguaggio di esposizione di un DB già popolato.

hdbsynonym: parlare con altri schemi

Per accedere a tabelle fuori dal tuo HDI container (es. tabelle di un altro modulo SAP), usi sinonimi:

synonym file 
// db/src/synonyms/customers.hdbsynonym
{
  "customers": {
    "target": {
      "schema": "EXTERNAL_SCHEMA",
      "object": "CUSTOMERS"
    }
  }
}
grants file 
// db/src/synonyms/customers.hdbgrants
{
  "EXTERNAL_GRANTOR": {
    "object_level": [
      {
        "schema": "EXTERNAL_SCHEMA",
        "name": "CUSTOMERS",
        "type": "TABLE",
        "privileges": ["SELECT", "INSERT"]
      }
    ]
  }
}
uso da CDS 
// nel modello CDS, usa il synonym come fosse una tabella locale
@cds.persistence.exists
entity customers {
  key ID  : String;
  name    : String;
  email   : String;
}

Indici, partizioni, performance

indici 
// indici secondari
@cds.persistence.index: [
  { name: 'idx_books_title',    columns: [title] },
  { name: 'idx_books_author',   columns: [author_ID] },
  { name: 'idx_books_composite', columns: [category_code, price], unique: false }
]
entity Books { ... }

// indice fulltext (HANA-specific)
@cds.persistence.index: [{
  name: 'ft_books_title',
  columns: [title, description],
  type: 'FULLTEXT',
  language: 'EN'
}]
entity Books { ... }
partition & storage 
// partitioning (HANA enterprise)
@cds.persistence.partitioning: {
  type: 'HASH',
  partitions: 4,
  columns: [tenant_ID]
}
entity Documents { ... }

// row vs column storage (HANA è columnar di default)
@cds.persistence.storage: 'row'
entity SessionData { ... }
Profiling

HANA Cloud ha SQL Analyzer e Plan Visualizer accessibili da SAP HANA Database Explorer. Per ogni query «lenta», esamina il piano: l'80% dei problemi sono indici mancanti o JOIN che generano cartesiani per via di filtri non pushabili.

Workflow di sviluppo — consigli pratici

  1. Modello prima. Definisci entity, association, view in SQLite. Quando il modello è stabile, abilita HANA.
  2. Profilo hybrid. cds bind ti permette di connettere il CAP locale a un HDI container reale. Così sviluppi su laptop ma con HANA vera.
  3. Branch per cambi schema. Le modifiche su HDI sono delta, ma DROP COLUMN o cambi di tipo sono distruttivi. Testa sempre su HDI di staging prima del prod.
  4. Cleanup vs preserve. cds deploy --to hana --auto-undeploy rimuove automaticamente artefatti orfani. In prod, gestisci undeploy.json esplicitamente.
  5. Monitoring. Configura cds.log per inviare a logger esterni (Loki, ELK, BTP Application Logging). Misura latenza su ogni handler.
  6. Performance budget. Definisci tetti per ogni endpoint (es. List Report < 500ms con 10k record). Se sfori, calcula view + indici + caching.
binding hybrid 
# workflow hybrid: dev locale con HANA reale
cf create-service hana hdi-shared bookshop-db-dev
cf create-service-key bookshop-db-dev dev-key
cds bind --to bookshop-db-dev:dev-key
cds watch --profile hybrid

Esercizio del capitolo

  1. Abilita HANA su un progetto esistente con cds add hana e cds add mta.
  2. Lancia cds build --production ed esamina la cartella gen/db/: identifica i file .hdbtable generati per ogni entity.
  3. Aggiungi un'annotation @cds.persistence.index con almeno 2 indici (uno semplice, uno composito) e verifica che vengano generati come .hdbindex.
  4. Crea una .hdbprocedure manuale che calcola una statistica e chiamala da un handler on(action).
  5. Crea una entity @cds.persistence.exists che referenzia una view nativa HANA che tu stesso crei prima (es. una calculation view via Database Explorer).
  6. Crea un .hdbsynonym verso uno schema esterno (anche fittizio) e usa la tabella sinonimica come entity CDS.
  7. Configura un binding hybrid: cds bind a un HDI container BTP e lancia cds watch --profile hybrid.
Bonus expert

Scrivi un .hdbcalculationview graficamente (via SAP HANA Database Explorer) che aggrega vendite per mese e country. Esponilo come entity CDS read-only e crea una projection di servizio con UI.LineItem.
