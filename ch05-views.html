Capitolo 05 · Views, projections, calculated

Views, projections, calculated

Il vero superpotere di CDS. Imparare a esprimere in modo dichiarativo quasi tutta la logica di lettura. Path expressions al posto delle JOIN, calculated elements, aggregazioni, view parametriche.

Perché le view contano

Le view sono il superpotere di CDS. Quando un'app CAP è scritta bene, gran parte della logica "di lettura" non è in handler JavaScript ma in view CDS: dichiarative, ottimizzate dal DB, automaticamente esposte come endpoint OData.

La regola pratica: se ti ritrovi a scrivere un handler after('READ') che modifica i dati restituiti, probabilmente quella logica dovrebbe essere una view CDS. Lascia che il DB faccia il lavoro pesante. Lascia che CDS dichiari il risultato.

View di base

Proiezioni e rinomina

cds 
entity Books {{
  key ID : UUID;
  title    : String;
  price    : Decimal(9,2);
  stock    : Integer;
  isbn     : String;
  createdBy: String;
}}

// View che mostra solo alcuni campi, con rinomina
view BooksLite as select from Books {{
  ID,
  title as name,        // rinomina
  price,
  stock as inventory    // rinomina
}};

La sintassi richiama SQL ma non è SQL: le view CDS vengono compilate in SQL del DB target. Su HANA diventano .hdbview.

Filtri WHERE

cds 
view ExpensiveBooks as select from Books {{
  ID, title, price
}} where price > 50;

view AvailableBooks as select from Books {{
  *  // tutti i campi
}} where stock > 0;

Sì, l'asterisco funziona. CDS espande tutti i campi dell'entity source. Comodo, ma in production preferisco specificare i campi: è più chiaro cosa la view espone e ti protegge da aggiunte involontarie di colonne sensibili nel source.

Path expressions

Questa è la feature che, una volta capita, cambia il modo in cui scrivi query in CAP. I path expressions sostituiscono le JOIN.

cds 
entity Books {{
  key ID : UUID;
  title  : String;
  author : Association to Authors;
}}

entity Authors {{
  key ID : UUID;
  name   : String;
  country: Association to Countries;
}}

// Path expression: niente JOIN, segui le association con la notazione punto
view BooksWithAuthor as select from Books {{
  ID,
  title,
  author.name as authorName,
  author.country.code as authorCountry,
  author.country.name as authorCountryName
}};

Cosa fa CDS dietro le quinte? Genera SQL con JOIN: LEFT OUTER JOIN Authors ON ... LEFT OUTER JOIN Countries ON .... Tu non devi scrivere niente. Ogni "punto" in un path expression è un JOIN implicito.

I path expressions funzionano anche nei filtri:

cds 
view ItalianBooks as select from Books {{
  ID, title, author.name as authorName
}} where author.country.code = 'IT';
Profondità arbitraria

Puoi andare in profondità quanto serve: order.customer.country.region.continent.name. Finché esistono le association nel modello, CDS genera tutti i join per te. Mai più JOIN ... ON ... AND ... scritti a mano.

Expand nelle view

I path expression "appiattiscono" le relazioni in colonne. Se invece vuoi che il risultato abbia struttura annidata (utile per API OData), usi expand:

cds 
view BooksNested as select from Books {{
  ID,
  title,
  author {{      // expand: include un oggetto annidato
    name,
    country.code as countryCode
  }}
}};

Restituisce JSON come:

risultato 
{{
  "ID": "...",
  "title": "...",
  "author": {{
    "name": "...",
    "countryCode": "IT"
  }}
}}

Per association to many, l'expand restituisce un array:

cds 
view AuthorsWithBooks as select from Authors {{
  ID,
  name,
  books {{          // to many → array
    title,
    price
  }}
}};

Calculated elements

Campi calcolati al volo, scritti come espressioni SQL:

cds 
entity OrderItems {{
  key ID : UUID;
  quantity   : Integer;
  unitPrice  : Decimal(9,2);
  vatRate    : Decimal(5,2);
  
  // Calculated on-read
  total      : Decimal(11,2) = quantity * unitPrice;
  totalWithVat : Decimal(11,2) = total * (1 + vatRate / 100);
}}

I calculated possono composare altri calculated (totalWithVat usa total). CAP risolve la dipendenza in fase di compile.

Stored vs on-read

Due varianti, con trade-off opposti:

cds 
// ON-READ: calcolato ogni volta che leggi (default)
total : Decimal(11,2) = quantity * unitPrice;

// STORED: calcolato all'INSERT/UPDATE, memorizzato
total : Decimal(11,2) = quantity * unitPrice stored;
VarianteVantaggiSvantaggi
on-readSempre coerente, niente storage extraCPU ad ogni read
storedVelocissimo in read, indicizzabileSpazio DB, ricalcolo automatico

Linea guida: stored se la query lo legge molto spesso e l'espressione è cara (join, aggregazioni). On-read se cambia spesso o è banale.

Aggregazioni e GROUP BY

Le view aggregate sono perfette per reporting e dashboard:

cds 
view SalesByAuthor as select from Books {{
  author.ID         as authorID,
  author.name       as authorName,
  count(*)          as bookCount  : Integer,
  sum(stock * price)as inventoryValue : Decimal(15,2),
  avg(price)        as avgPrice : Decimal(9,2),
  max(price)        as maxPrice : Decimal(9,2)
}} group by author.ID, author.name;

Tre dettagli importanti:

  1. Le funzioni standard SQL (count, sum, avg, min, max) sono supportate
  2. I campi aggregati richiedono di specificare il tipo (: Integer, : Decimal(...))
  3. Path expressions funzionano anche nel group by

Aggiungi un having per filtri sull'aggregato:

cds 
view TopAuthors as select from Books {{
  author.name as authorName,
  count(*) as bookCount : Integer
}} group by author.name
  having count(*) > 5;

Union, join, subquery

cds 
// UNION ALL: combina due query
view AllContacts as 
  select from Customers {{ name, email, 'customer' as type : String }}
  union all
  select from Suppliers {{ name, email, 'supplier' as type : String }};

// JOIN esplicita (se path expression non basta)
view BookSalesReport as
  select from Books as b
    inner join Sales as s on s.book = b.ID
  {{
    b.title,
    sum(s.quantity) as sold : Integer
  }} group by b.title;

// Subquery
view BooksAbovAvg as select from Books {{
  ID, title, price
}} where price > (select avg(price) from Books);

View parametriche

Le view possono accettare parametri al momento della query, generando SQL parametrico:

cds 
view BooksByPriceRange(min : Decimal, max : Decimal) as
  select from Books {{ ID, title, price }}
  where price between :min and :max;

Dal client (lato handler o servizio OData):

in handler JS 
const results = await SELECT.from(BooksByPriceRange).where({{ 
  min: 10, max: 50 
}});

Su HANA queste diventano .hdbview con parametri reali, gestiti dal motore HANA. Performance eccellenti.

Projection vs view

Due costrutti che si somigliano, ma con uso diverso:

Aspettoview ... as select fromentity ... as projection on
Dove viveIn db/ tipicamenteIn srv/ tipicamente
ScopoTrasformare datiEsporre dati al client
AnnotabileSìSì (e di solito è qui che si annota per UI)
PersistenzaView SQL sul DBNon persistita
Sintassi similePiù SQL-likePiù CDS-like

Pattern: usa view nel layer DB per trasformazioni dati che hanno senso a livello di persistenza. Usa projection nei service per modellare l'esposizione al client (rinominare campi, escludere colonne sensibili, applicare filtri di sicurezza).

cds 
// db/views.cds
view ActiveOrders as select from Orders {{
  *
}} where status != 'archived';

// srv/service.cds
service OrderService {{
  entity Orders as projection on db.ActiveOrders
    excluding {{ createdBy, modifiedBy }};
}}

  1. Una view SessionSummary che mostri per ogni sessione: titolo, nome speaker, paese speaker, numero di attendees

  3. Una view parametrica SessionsByDateRange che prenda due date e restituisca le sessioni in quel range
  4. Una view con UNION di sessioni recenti (ultimi 30 giorni) e future (prossimi 30 giorni), con un campo type per distinguerle
