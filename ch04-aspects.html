Capitolo 04 · Aspects, mixins, riusabilità

Aspects, mixins, riusabilità

Smettere di ripetere codice nel modello dati. Aspects predefiniti, pattern custom, localized, aspect bibliotecari standard SAP. Il modo idiomatico CAP di scrivere modelli DRY.

Cosa sono gli aspect

Un aspect in CDS è un blocco riusabile di definizioni — campi, association, annotation — che puoi mescolare in più entity senza ripetere codice. Pensa agli aspect come ai mixin o traits di altri linguaggi.

cds 
// Definisci una volta
aspect Auditable {{
  createdAt  : Timestamp default $now;
  createdBy  : String    default $user;
  modifiedAt : Timestamp;
  modifiedBy : String;
}}

// Usa ovunque
entity Books : Auditable {{
  key ID : UUID;
  title  : String;
}}

entity Authors : Auditable {{
  key ID : UUID;
  name   : String;
}}

Entrambe le entity ora hanno i quattro campi audit, definiti in un posto solo. Se domani vuoi cambiarli (aggiungere deletedAt, per esempio), tocchi un solo file.

Sintassi della composizione

entity Books : Auditable { ... } usa i due punti per estendere con un aspect. Puoi metterne più di uno: entity Books : Auditable, Tagged, Reviewable { ... }.

Aspect predefiniti

CAP fornisce out-of-the-box un set di aspect comuni in @sap/cds/common. Vediamoli uno per uno — risparmiano centinaia di righe di codice nel progetto medio.

cuid: chiave UUID standard

cds 
using {{ cuid }} from '@sap/cds/common';

entity Books : cuid {{
  title : String;
}}

// Equivalente a:
entity Books {{
  key ID : UUID;
  title  : String;
}}

Sembra banale — risparmi una riga. Ma quando hai 50 entity, sono 50 righe di chiavi tutte uguali sostituite da un singolo aspect riconoscibile a colpo d'occhio. E se domani decidi di usare un tipo diverso per le chiavi, lo fai in un punto solo (estendendo cuid).

managed: audit trail automatico

cds 
using {{ managed }} from '@sap/cds/common';

entity Books : cuid, managed {{
  title : String;
}}

L'aspect managed aggiunge quattro campi: createdAt, createdBy, modifiedAt, modifiedBy. Ma fa molto di più — CAP gestisce automaticamente questi campi a runtime:

  • Su INSERT: imposta createdAt + createdBy
  • Su UPDATE: imposta modifiedAt + modifiedBy
  • I campi sono read-only nell'API: il client non può sovrascriverli

Questa è la potenza degli aspect in CAP: non sono solo "shortcut sintattici", portano comportamento runtime.

temporal: versionamento storico

cds 
using {{ temporal }} from '@sap/cds/common';

entity Prices : temporal {{
  key product : Association to Products;
  amount      : Decimal(9,2);
}}

temporal aggiunge validFrom e validTo alle chiavi, trasformando l'entity in una "time series". Il client può fare query "as-of":

OData time queries 
GET /Prices?$at=2025-06-15T00:00:00Z
# Restituisce solo i prezzi validi a quella data

GET /Prices?$from=2025-01-01&$to=2025-12-31
# Restituisce tutti i prezzi attivi in quel range

Versionamento storico automatico, senza scrivere logica.

Localized: multilingua zero-effort

Non è un aspect ma un modificatore di tipo. Lo metto qui perché è uno dei trucchi più potenti di CDS:

cds 
entity Products : cuid, managed {{
  title       : localized String;
  description : localized LargeString;
  category    : String;  // non localizzato
}}

Cosa genera CAP a partire da questo? Tre artefatti:

  1. Tabella Products con le colonne in lingua "di base"
  2. Tabella Products_texts con (locale, ID, title, description)
  3. View localized.Products che fa una join automatica in base alla lingua del request

Il client OData vede semplicemente title e description nella lingua giusta — CAP ispeziona il header Accept-Language o il parametro sap-language e fa la join corretta. Per modificare le traduzioni, l'entity Products.texts è automaticamente esposta come associazione.

Best practice

Usa localized per qualsiasi testo visibile all'utente finale: titoli, descrizioni, label, messaggi. Non per dati interni (codici, status, ID esterni). Decidere bene fin dall'inizio risparmia migrazioni dolorose dopo.

CodeList, Countries, Currencies, Languages

Sono pattern standard per i codici di "lookup table" — sigle paese, valute, lingue, ecc. CAP fornisce:

cds 
using {{ 
  sap.common.Countries, 
  sap.common.Currencies, 
  sap.common.Languages 
}} from '@sap/cds/common';

entity Customers : cuid {{
  name     : String;
  country  : Association to Countries;
  currency : Association to Currencies;
}}

Queste tre entity sono già modellate, già localizzate (i nomi paese in più lingue!), e all'attivazione del progetto CAP le popola con tutti i codici ISO standard. Mai più lookup table custom per cose standard.

Tutte estendono il pattern CodeList, che puoi usare per i tuoi codici custom:

cds 
using {{ sap.common.CodeList }} from '@sap/cds/common';

entity OrderStatuses : CodeList {{
  key code : String(10);
  // Aggiunge automaticamente: name (localized) e descr (localized)
}}

Aspect custom

Crei i tuoi aspect quando vedi pattern ripetuti nel tuo modello. Esempi reali da progetti di produzione:

cds 
// Soft delete pattern
aspect SoftDeletable {{
  isDeleted : Boolean default false;
  deletedAt : Timestamp;
  deletedBy : String;
}}

// Money pattern (importo + valuta)
aspect Priced {{
  amount   : Decimal(15,2);
  currency : Association to Currencies;
}}

// Geo pattern
aspect Located {{
  latitude  : Decimal(9,6);
  longitude : Decimal(9,6);
}}

// Approval workflow
aspect Approvable {{
  status     : String(10) default 'draft';
  approvedAt : Timestamp;
  approvedBy : String;
  rejectReason : String(500);
}}

Convenzione: gli aspect custom in un file db/aspects.cds o db/common.cds, importati ovunque servano.

Composizione multipla

Un'entity può ereditare da più aspect contemporaneamente. È questo che rende il sistema espressivo:

cds 
entity Invoices : 
    cuid, managed, Priced, Approvable {{
  customer : Association to Customers;
  dueDate  : Date;
  items    : Composition of many InvoiceItems 
               on items.invoice = $self;
}}

Questa entity ha:

  • Da cuid: chiave ID UUID
  • Da managed: createdAt, createdBy, modifiedAt, modifiedBy
  • Da Priced: amount, currency
  • Da Approvable: status, approvedAt, approvedBy, rejectReason
  • Specifico: customer, dueDate, items

Sedici campi in totale, ma il file CDS è cortissimo e si legge come una specifica di business: "una Invoice è qualcosa di identificabile, tracciato, con prezzo e approvabile".

extend vs annotate

Due verbi che si confondono spesso. Servono entrambi a "modificare" cose già definite altrove, ma in modi diversi:

  • extend: aggiunge nuovi campi/elementi a un'entity esistente
  • annotate: aggiunge/modifica annotation, senza toccare la struttura
cds 
// Estendi un'entity esterna aggiungendo campi
extend Books with {{
  rating : Decimal(3,2);
  tags   : array of String;
}}

// Aggiungi annotation a un'entity esistente
annotate Books with @(
  UI.LineItem: [
    {{ Value: title }},
    {{ Value: author.name }}
  ]
);

// Annota un singolo campo
annotate Books:title with @Common.Label: 'Titolo';

Pattern fortemente raccomandato: tieni le annotation UI in file separati (es. app/books-ui.cds), non mescolate al modello dati. Ti semplifica la vita e separa nettamente le responsabilità.

Esercizio del capitolo

Refactora il modello del Capitolo 3 (Conference Management) usando aspect:

  1. Aggiungi cuid e managed ovunque sensato
  2. Definisci un aspect custom Schedulable con startDate, endDate, duration
  3. Applica Schedulable a Conferences e Sessions
  4. Rendi localized i campi di testo visibili agli attendees
  5. Sostituisci eventuali colonne paese/lingua con Association to Countries/Languages
  6. Verifica con cds compile --to sql che lo schema generato sia compatto e pulito
